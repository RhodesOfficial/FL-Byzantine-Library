# 创新算法分阶段工作流

供 D1、D2、D3 复用。每阶段只在上一阶段得到用户确认后开始；3B 还需要用户明确说“进入 3B”。每阶段完成后检查工作区，列出拟提交文件，排除并报告非预期文件，再提交；不推送。

| 阶段 | 输入 | 输出 | 检查点 | 决策门 |
| --- | --- | --- | --- | --- |
| 1 核心类 | 指定 Python 环境验证、`PROJECT_MAP` 桥接契约、对应创新方向描述；必要时定向读取本地论文 | 独立聚合器类、mock 单测、参数与输入需求判断 | 指定解释器的 PyTorch/CUDA 验证；模块行为、回退、限额、方向单测；现有桥接回归；提交前 `git status` | 若算法依赖桥接层没有的必要输入，先报告缺口；否则提交阶段 1 并等待确认 |
| 2 桥接与 smoke | 阶段 1 提交、桥接上下文与根集加载器、现有 CLI | 注册与需求声明、参数映射、可复制的最小端到端命令 | 聚合器确实被 FLGo 调用；输出有限且形状正确；现有七聚合器回归；数据缺失时报告数据集、期望目录和额外处理 | smoke 通过且无意外文件后提交，等待确认 |
| 3A 跑通验证 | 阶段 2 提交、现成 FLGo 基准、本地 A/B 硬件、用户准备的数据集 | `run_d1_full.py --profile smoke`、D1 与 FedAvg 的总体和尾类准确率、耗时与稳定性报告 | 固定科学参数；完整根类别覆盖；检查曲线、有限值、回退率、时间和显存；不把通过解释为核心机制成立 | 给出继续 3B、调整 D1 或停止的建议；提交并等待明确的“进入 3B” |
| 3B 完整实验 | 用户明确授权、3A 报告、CIFAR-10-LT/CIFAR-100-LT 数据与后端需求 | `--profile full`、精简单元清单、消融与压力实验、16GB/24GB 耗时估计 | 主场景、四种子、关键消融及一个代表性恶意比例扫描；总单元数少于 100；核验核心机制与资源成本 | 完整实验设计与代码核对后提交；运行平台由用户按时间和显存估计决定 |

## 阶段 1 的实际执行记录

使用 `E:\anaconda3\python.exe` 验证得到 `torch 2.5.1`、CUDA 可用。先阅读项目映射第 2、3 节和方向一，再核对 `_BaseAggregator`、`AggregationContext`、`root_data` 加载器与 FLGo 计算器接口。BR-DRAG 的具体校准式只定向查阅本地 Xiao 等论文第 IV.B–C 节。随后实现三个 D1 模块并用 mock 根数据测试；阶段 1 不修改桥接层，也不注册算法。

## 每阶段提交记录规则

提交前执行 `git status`，明确列出本阶段 `git add` 的路径。缓存、实验输出、任务目录和已有未跟踪文件不得混入提交；出现未预期文件时先报告，等用户确认处置后再提交。消息格式为 `phase<N>: <一句话描述>`，只提交不推送。
