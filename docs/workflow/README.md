# 双 agent 工作流操作手册

> 这份手册写给作者本人。照着做，不需要再找任何人写 prompt。

## 一、核心思路

- **仓库是唯一的消息通道。** 审查 agent 和执行 agent 不直接对话，也不靠你转述。它们通过两个文件交接：`TO_EXECUTOR.md`（审查 → 执行）和 `TO_REVIEWER.md`（执行 → 审查）。
- **提示词固定不变。** 你每次只复制粘贴下面两句话。所有规则写在 `ROLE_*.md` 里，所以不会再有"prompt 越改越偏"的问题。
- **状态只认文件。** 项目当前在哪一步，以 `STATE.md` 为准，不以任何会话的记忆为准。会话可以随时新开。

## 二、文件一览

| 文件 | 谁写 | 作用 |
|---|---|---|
| `ROLE_REVIEWER.md` | 你同意后才改 | 审查 agent 的固定职责与格式 |
| `ROLE_EXECUTOR.md` | 你同意后才改 | 执行 agent 的固定职责与格式 |
| `STATE.md` | 审查 agent（"作者约束"一节由你填） | 当前节点、进度、风险、待你决策的事、决策日志 |
| `TO_EXECUTOR.md` | 审查 agent，每次覆盖 | 下一份任务单 |
| `TO_REVIEWER.md` | 执行 agent，每次覆盖 | 上一次的交付单 |
| `PLAIN_GUIDE.md` | 审查 agent 在课题有重大变化时更新 | 给你看的白话导读 |

历史记录全部在 git log 里，所以交接文件每次直接覆盖。

工程修复按两份ROLE执行：单任务最多6次（含首次），真实入口仍最多3次且不超冻结余额，两者分账。P第6轮已用满3次，6次留出排错余地；同一异常签名在两次实际尝试中连续仍在即封存，资源硬限照旧，不无限循环。
一张单要留出“写完、跑完、再改一次”：新实现通常分配至少3次修订及2次语法/CPU验证；已有实现的定点修复至少2次修订及2次语法/CPU验证，最后一组留给验证后修正，首次成功即交审。上限、已用、余额、本单分配分别列出；续单累计不清零，运行前修改也计数，两轮合用一个资源包络，不能把全局6次切成反复无修复余地的“本单1次”。冻结次数只能按授权同步合同，历史超额不追认；本次D3具体授权见裁决v8。
任务单与ROLE冲突时，工程修复条款优先；符合修复条件时，只有已产生新科学结果或任务单写明工程修复剩余0及依据才能禁止。自检失败或异常先分类；只读辅助程序失败可同单再跑一次相同计算，不计正式事件入口，不改历史资源FAIL。
开工读取规则、状态、Git身份和少量旧元数据属于有限启动准备：已知成本与未知分列，缺完整外部I/O事前上界不单独封存；受限程序的启动/下一动作仍须守卫。旧未知和历史FAIL保留，合成验证不开放科学入口。
新次数在作者同意后从下一张任务单起生效；历史任务单、裁决、已提交交付和冻结P/F次数不改，已关闭阶段不追加。冻结估算超过剩余预算不派真实入口，科学禁重跑和作者拍板范围不变。

## 三、固定提示词（直接复制）

**给审查 agent：**

```
读 docs/workflow/ROLE_REVIEWER.md，然后按其中"每次被唤醒时的固定流程"处理 docs/workflow/TO_REVIEWER.md。完成后提交，并只回复一句话结论和是否需要我拍板。
```

**给执行 agent：**

```
读 docs/workflow/ROLE_EXECUTOR.md，然后按其中"每次被唤醒时的固定流程"执行 docs/workflow/TO_EXECUTOR.md。完成后提交，并只回复一句话结果、FAIL 条数和是否有阻塞。
```

两句话每次都一样。不要往里加你自己的理解，也不要让其他模型改写。

## 四、一个回合怎么走

```
审查 agent 写 TO_EXECUTOR.md  →  你检查 ①  →  执行 agent 干活，写 TO_REVIEWER.md  →  你检查 ②  →  审查 agent 裁决 ……
```

### 你在 ① 处检查（审查 agent 跑完之后，约 2 分钟）

1. `git log -1` 有一条 `review(...)` 开头的新提交。
2. `TO_EXECUTOR.md` 有"通过判据"并且逐条编号，有"明确不做"和"资源上限"。
3. `STATE.md` 的"待作者决策"是否为"无"。不是"无"就按第五节处理，处理完再进入下一步。
4. 篇幅没有明显失控（任务单大约 100 行以内）。

都满足后，把执行 agent 的固定提示词发给执行 agent。

### 你在 ② 处检查（执行 agent 跑完之后，约 2 分钟）

1. `git log -1` 有一条 `exec(...)` 开头的新提交。
2. `TO_REVIEWER.md` 的"判据自评"表格里，每条判据都有 PASS/FAIL。
3. 看"阻塞"和"异议"是不是"无"。不是"无"也没关系，直接交给审查 agent 处理。
4. `git status` 干净，没有遗留的未提交文件。
5. 推送前执行 `git show --stat HEAD`，二进制文件一栏没有超过 20000000 bytes 的条目。有的话，回复执行 agent："按 ROLE_EXECUTOR.md 的大文件规则处理后重新提交。"

都满足后，把审查 agent 的固定提示词发给审查 agent。

### 推送

每完成一次"审查 → 执行 → 审查"，你执行一次 `git push origin feature/direction-a`。

## 五、你的角色：项目负责人，不是技术评审

你不需要判断公式和代码对不对，那是两个 agent 互相检查的事。你负责下面这些 AI 做不到或者做不好的事：

1. **提供约束。** 在 `STATE.md` 的"作者约束"一节填写答辩时间、每周可投入时间、导师要求。没有这些信息，agent 无法判断什么值得做、什么该砍。
2. **看过程信号。** 你看不懂内容，但看得懂下面这些信号：
   - 同一个节点来回超过 3 次还没通过；
   - 连续两周 `STATE.md` 的"当前节点"没有变化；
   - 交付里出现"预算耗尽""证据不足"却没有下一步计划；
   - 文档越写越长，代码和实验结果却没增加。

   出现任何一个，就用第七节的"元审查提示词"新开一个会话。
3. **拍板选择题。** 只有 `STATE.md` 里出现"待作者决策"时你才需要做决定。它会按固定格式给你选项和推荐项：
   - 看不出问题，就回复审查 agent："采纳 D<编号> 的推荐选项"。
   - 标注"建议先问导师"的（通常是换方向、收窄论文主张），把白话背景和选项发给导师，再把导师意见原样回复给审查 agent。
4. **逐步学会讲自己的课题。** 答辩时没有 agent 帮你。每周花一点时间用第七节的"讲解提示词"学一个概念，从 `PLAIN_GUIDE.md` 开始。

## 六、常见情况怎么处理

| 情况 | 你怎么做 |
|---|---|
| agent 在会话里问你技术问题 | 回复："请按 ROLE 文件自行判断并在交接文件里写明理由；需要我决定的，按'待作者决策'格式写进 STATE.md。" |
| 你想确认 agent 做得对不对 | 不要问"你确定吗"。把它交给另一个 agent：执行的结果交给审查 agent 用固定提示词审，审查的任务单如果执行者觉得有问题，会写在"异议"里 |
| 两个 agent 意见反复冲突 | 审查 agent 有判据的最终解释权；超过 2 个回合，它会写成"待作者决策"给你选 |
| agent 回复很长、满是免责声明 | 回复："按 ROLE 文件的篇幅上限和'少用免责声明'规则重写交接文件。" |
| agent 好像忘了之前的事、说法前后矛盾 | 新开一个会话，发同样的固定提示词。状态都在文件里，不会丢 |
| 你想改流程规则 | 通常单独起草、你同意后再提交；你已明确要求本次改规则时，审查 agent 直接先改规则、再按新规则裁决和派单，一次提交。未获直接授权时，仅同节点连续两次无新增结果工程阻塞或任务单与ROLE冲突时起草。执行 agent 不改ROLE和判据，能动性只放在异议和工程修复 |
| 两个 agent 同时在跑 | 不要这样做。同一时间只让一个 agent 操作仓库 |

## 七、另外三个固定提示词

**元审查**（每周一次，或出现第五节第 2 条的信号时；每次新开会话）：

```
你是一个不参与本项目执行的外部审查者。读 docs/workflow/PLAIN_GUIDE.md、docs/workflow/STATE.md 和最近两周的 git log。用不超过一页、不含公式的白话回答：1) 这段时间推进了哪个科学问题；2) 离检查点 M 还差哪些节点，哪些可以合并或删掉；3) 最大的风险是什么。不要修改任何文件。
```

**讲解**（你想学的时候；可以发给任何一个 agent）：

```
读 docs/workflow/PLAIN_GUIDE.md 和 docs/workflow/STATE.md。用本科生能听懂的话，结合一个具体例子，给我讲清楚当前节点在做什么、为什么要做。最后出 3 道简单的题考我，等我回答后再告诉我对错。不要修改任何文件。
```

**给导师的月报**（每月一次）：

```
读 docs/workflow/PLAIN_GUIDE.md、docs/workflow/STATE.md 和本月的 git log，写一份给导师看的一页进展汇报：研究问题、本月完成、关键结果（只写已经有证据的）、遇到的问题、下月计划、需要导师意见的事项。写入 docs/workflow/reports/<年-月>.md 并提交。
```

## 八、会话与模型

### 什么时候新开会话

原则：**一个检查点节点，配一对会话**（一个审查、一个执行）。同一节点内的多个回合在原会话里继续，每次都发同样的固定提示词。

出现以下任一情况，就给对应的 agent 新开会话：

1. `STATE.md` 的"当前节点"变了，进入了新节点。
2. `ROLE_*.md` 被修改过。
3. agent 出现健忘或矛盾：违反 ROLE 规则、引用过时的状态、和自己之前的说法冲突。
4. 界面提示上下文已被压缩，或者会话已经非常长。

元审查每次都新开会话。讲解和月报随意。

旧会话不要删，可以留着查历史，但不要再用它们推进工作。

### 用哪个模型

| 用途 | 模型与推理强度 | 理由 |
|---|---|---|
| 审查 agent，日常裁决和派活 | GPT-6 Astra · High | 科研推理是 Astra 明显领先的领域 |
| 审查 agent，关口总裁决（G1.3、G2.3、G3.3、4.2、M）或待作者决策 | GPT-6 Astra · Extra High | 这类决定影响论文走向，值得多花时间 |
| 执行 agent，日常编码和实验 | GPT-6.1 Sol · High | 软件工程能力与 Astra 持平，成本约为 1/5 |
| 执行 agent，同一异常签名连续两次仍在 | 封存交审；后续已授权任务可用 GPT-6.1 Sol · Extra High | 换模型或推理强度不追加次数 |
| 元审查 | GPT-6.1 Sol · Extra High | 故意和审查 agent 用不同模型，减少同一模型的盲点 |
| 讲解、月报 | GPT-6.1 Sol · Medium | 任务简单 |

额度紧张时，先把审查 agent 的日常裁决降到 Astra · Medium，不要降执行 agent。

## 九、第一次实操：走完"G1.2 第一段"这个节点

起点：执行 agent 已经交了 G1.2 第一段（commit 948cfda），但还没有被审查。交付单已经整理在 `TO_REVIEWER.md` 里。

**第 0 步：准备（只做一次）**
1. 把包含 `docs/workflow/` 的这次修改合并进 `feature/direction-a`，然后本地执行 `git checkout feature/direction-a` 和 `git pull origin feature/direction-a`。
2. 打开 `docs/workflow/STATE.md`，填写"作者约束"一节，提交：`git commit -am "state: fill author constraints"`。
3. 读一遍 `PLAIN_GUIDE.md`。

**第 1 步：审查 agent 裁决第一段**
- 新开一个审查 agent 会话（GPT-6 Astra），发送"给审查 agent"的固定提示词。旧会话里积累了 DeepSeek 时期的指令，会和新规则冲突，所以第一次一定要新开。执行 agent 在第 2 步也新开。
- 预期结果：它会回答 `TO_REVIEWER.md` 末尾的 3 个问题，包括是否采纳 ε_num=2e-6、是否授权第二段、尾类 recall=0 怎么处理；更新 `STATE.md`；把第二段（或它认为更该先做的事）写成 `TO_EXECUTOR.md`；然后提交。
- 你做第四节的检查 ①。如果"待作者决策"里有内容，比如它建议重新准备参考模型而这会多花资源，就按第五节第 3 条回复。

**第 2 步：执行 agent 干活**
- 新开一个执行 agent 会话（GPT-6.1 Sol），发送"给执行 agent"的固定提示词。
- 预期结果：它按任务单实现和运行，覆盖写 `TO_REVIEWER.md`，然后提交。
- 你做第四节的检查 ②。

**第 3 步：审查 agent 再次裁决**
- 回到第 1 步的审查会话，再发一次"给审查 agent"的固定提示词。如果修了几轮后节点前进了，按第八节为下一个节点新开会话。
- 如果通过，`STATE.md` 的当前节点会前进（例如进入 P 或 G1.3 的准备）；如果不通过，会有一份新的 `TO_EXECUTOR.md` 列出要修的条目，回到第 2 步。
- 执行 `git push origin feature/direction-a`。

**第 4 步：自检你学会了没有**
- 发"讲解提示词"，看你能不能答对 3 道题。

走完这一轮，后面每个节点都是第 1–3 步的重复。

## 十、旧文档怎么办

- `docs/` 下已有的可行性报告、检查点、研究合同、各次裁决全部保留，作为研究依据和历史记录。审查 agent 会按需引用其中的章节。
- 研究合同 `DIRECTION_A_PROTOCOL_FREEZE_v1.md` 仍是阈值和冻结项的权威来源，由审查 agent 维护。
- `docs/INNOVATION_WORKFLOW.md` 是 D1 时期的旧流程，方向 A 不再使用。
